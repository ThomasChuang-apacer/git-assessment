請使用 `ui-ux-pro-max` 技能，重新設計目前專案中「離線 Git 題目測驗程式」的 UI/UX，並直接完成實作與驗證。

## 一、專案現況

這是一個完全離線運作的 HTML 測驗程式，目前所有核心功能都已完成：

- 輸入受測者姓名
- 進行六題 Git 測驗
- 計算並顯示成績
- 保存歷史測驗紀錄
- 使用 localStorage 保存資料
- 匯出測驗結果

本次工作僅針對 UI/UX、響應式版面、可用性與無障礙體驗進行改造，不重新設計業務邏輯。

## 二、首要原則

現有功能完整性優先於視覺改造。

不得破壞、移除或改變：

- 題目內容、題目順序與答案
- 計分規則與結果判定
- 姓名輸入與驗證邏輯
- localStorage 的 key、資料結構及讀寫行為
- 歷史紀錄保存與顯示邏輯
- 匯出檔案的內容、欄位、格式與編碼
- 既有函式名稱與函式呼叫關係
- HTML 元素既有的 `id`、`name`、`value`、`data-*`
- inline event handler 與 JavaScript 事件綁定
- JavaScript 使用的 class、CSS selector 或 DOM 相對位置

修改 HTML 結構之前，先檢查 JavaScript 是否依賴：

- `querySelector`／`querySelectorAll`
- `getElementById`
- class selector
- parent／children／sibling 關係
- 元素順序
- 表單提交行為
- 動態建立的 HTML
- innerHTML 產生的內容

若某項結構可能影響功能，應保留原結構，只透過 CSS 改善外觀。

## 三、離線限制

程式必須在沒有網路連線的環境下完整運作。

禁止：

- CDN
- Google Fonts
- 外部 CSS 或 JavaScript
- 外部圖片、圖示或背景資源
- 從網路載入的套件
- 新增 npm 或其他相依套件
- CSS `@import`
- 任何需要 HTTP／HTTPS 請求的資源

可以使用：

- 系統內建字型
- 純 HTML、CSS、JavaScript
- CSS 繪製的裝飾
- 直接內嵌於 HTML 的 SVG
- 專案中原本已存在的本機資源

中文字型優先使用：

`"Microsoft JhengHei", "PingFang TC", "Noto Sans TC", system-ui, sans-serif`

程式碼或 Git 標籤可使用：

`Consolas, "Cascadia Code", "Courier New", monospace`

不要因字型不存在而影響版面。

## 四、設計目標

整體風格應具備：

- 專業、現代、清楚
- 適合企業內訓、教育訓練與技能檢定
- 帶有 Git、終端機及開發者工具的視覺語言
- 資訊層級明確
- 長時間閱讀舒適
- 避免過度裝飾和常見的 AI 生成感

建議視覺方向：

- 中性色背景搭配高對比文字
- 使用 Git 橘色作為主要品牌強調色
- 深灰、石墨色或藍灰色作為介面基礎色
- 卡片使用清楚邊界與輕微陰影
- 圓角適中，不要所有元素都使用膠囊造型
- 程式碼或 Git 指令使用等寬字體
- 圖示僅使用簡潔的內嵌 SVG
- 不使用 emoji 代替操作圖示

避免：

- 大面積或高飽和漸層
- Glassmorphism
- 過多陰影與發光效果
- 過度圓角
- 不必要的動畫
- 大量紫色／粉紅色 AI 風格
- 只為裝飾而存在的資訊卡
- 低對比灰色文字

## 五、畫面與使用流程

### 1. 開始畫面

應清楚呈現：

- 測驗名稱
- 簡短說明
- 總題數
- 姓名輸入欄位
- 開始測驗按鈕
- 查看歷史紀錄的入口

姓名欄位需要：

- 明確且持續可見的 label
- 必填提示
- 錯誤訊息
- 清楚的 focus 狀態
- 按 Enter 可以開始測驗，但不得繞過既有驗證

主要按鈕必須明顯，但不要讓其他操作難以辨識。

### 2. 作答畫面

應清楚呈現：

- `第 X 題，共 6 題`
- 視覺化進度條
- 題目文字
- 選項
- 必要的導覽按鈕
- 當前選取狀態

題目和選項必須：

- 有足夠字級與行距
- 每個選項具有足夠的可點擊範圍
- 整列選項都能點選
- hover、focus、selected 狀態彼此清楚
- 鍵盤使用者可以操作
- 不以顏色作為唯一狀態提示
- 手機上避免選項過度擁擠

若既有程式支援上一題、下一題或提交按鈕，重新設計其視覺層級，但不得增加不存在的流程或改變原本行為。

### 3. 結果畫面

應優先顯示：

- 受測者姓名
- 得分
- 答對題數
- 總題數
- 答對率
- 完成時間或既有時間資訊
- 匯出結果按鈕
- 重新測驗或返回操作

結果資訊應容易掃讀，避免只有一個巨大分數而缺少上下文。

答對與答錯不能只用綠色、紅色區分，應同時使用文字、符號或圖示。

### 4. 歷史紀錄

歷史紀錄需要方便比較：

- 姓名
- 測驗日期／時間
- 分數
- 答對率
- 既有操作按鈕

桌面版可使用清楚的表格；手機版應避免水平捲動，可改為堆疊式紀錄卡片。

不得改變紀錄排序、資料欄位或刪除／清除行為。

### 5. 空白與錯誤狀態

改善以下狀態：

- 尚未輸入姓名
- 尚未選擇答案
- 尚無歷史紀錄
- 匯出成功或失敗
- localStorage 無法使用
- 資料內容異常

錯誤訊息應：

- 靠近相關欄位或操作
- 清楚說明問題及處理方式
- 不只依賴紅色
- 不使用瀏覽器 `alert()` 取代所有介面回饋，除非這是既有功能且修改會提高風險

## 六、響應式要求

至少檢查以下寬度：

- 375px
- 768px
- 1024px
- 1440px

要求：

- 不得出現非預期的水平捲動
- 主要內容設定合理的最大寬度
- 手機版保留足夠左右間距
- 手機按鈕與選項觸控範圍至少約 44×44px
- 小螢幕上主要操作應容易觸及
- 長題目、長姓名與長紀錄內容不得破版
- 結果與歷史紀錄在手機上仍容易閱讀

## 七、無障礙要求

至少符合以下要求：

- 一般文字與背景對比度達 WCAG AA
- 所有可操作元素具有明顯的 `:focus-visible`
- 使用鍵盤可以完成姓名輸入、作答、提交與匯出
- 使用語意化的 button、label、fieldset、legend 或適合的 ARIA
- 不移除瀏覽器原生 outline，除非提供更清楚的替代樣式
- 錯誤與狀態訊息可使用 `aria-live` 呈現
- 進度資訊同時提供文字，不只呈現進度條
- 動畫遵守 `prefers-reduced-motion`
- 不使用顏色作為唯一資訊提示

新增 ARIA 前先確認語意正確，避免重複或互相衝突的標籤。

## 八、動畫與互動

允許使用簡短、克制的互動效果：

- hover
- focus
- 選項選取
- 畫面狀態切換
- 進度更新

動畫時間建議控制在 150–250ms。

不得加入：

- 自動播放動畫
- 大幅位移
- 背景持續動畫
- 影響答題速度的過場
- 造成暈眩或分散注意力的效果

請依下列順序執行：

1. 讀取並分析目前所有相關 HTML、CSS、JavaScript。
2. 建立「功能與 DOM 相依關係清單」。
3. 簡要列出目前主要 UI/UX 問題。
4. 提出精簡的改造方案與設計系統：
   - 色彩
   - 字體
   - 間距
   - 圓角
   - 陰影
   - 按鈕
   - 表單
   - 題目選項
   - 狀態樣式
5. 完成分析後直接實作，不必等待確認；只有發現需求衝突或高風險修改時才詢問。
6. 優先修改 CSS。
7. 僅在改善語意、響應式或無障礙確實需要時調整 HTML。
8. 除非功能修復或 UI 狀態同步確實需要，否則不要修改功能性 JavaScript。
9. 不進行與 UI/UX 無關的重構。
10. 不建立新的框架、建置流程或套件相依。

建議使用 CSS custom properties 統一管理：

- 色彩
- 字體
- 間距
- 圓角
- 陰影
- transition
- focus ring
