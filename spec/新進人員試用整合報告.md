## 二、嚴重問題：影響判分可信度與核心流程（P0）

> [!CAUTION]
> 以下 5 項直接影響「考試結果是否可信」或造成每位受測者必遇的嚴重干擾，建議在正式上線前務必修復。

### P0-1：`[共同驗證]` Task 05 新測驗必現「需要套用新版題目」誤報（重設後仍在）
- **現象**：剛建立的全新測驗進入 Task 05，一律顯示警告 *「此測驗建立於舊版第五題。請使用『重設本題』套用遠端限定分支情境。」*，照做重設或通過全部 7 項檢查後警告仍不消失。
- **根因**：[template_builder.py](file:///C:/Users/2606854/.gemini/antigravity/worktrees/git-assessment/newcomer_ux_evaluation/app/template_builder.py#L12) 已升版至 `VERSION = 7` 並寫入 `assessment.templateVersion = "7"`，但 [services.py](file:///C:/Users/2606854/.gemini/antigravity/worktrees/git-assessment/newcomer_ux_evaluation/app/services.py#L338) 仍寫死 `version.stdout == "5"`。
- **解法**：改為與 `TemplateBuilder` 共用常數並比對 `int(version) >= 5`，新增回歸測試驗證新建測驗的 Task 05 不應出現相容性警告。

### P0-2：`[共同驗證]` Task 04 雙重判分漏洞（不解 Conflict、不 Fetch/Rebase 皆可 7/7 通過）
- **漏洞 A `[Claude 發現]`（Conflict 標記未清仍通過）**：`rebase` 發生衝突後不解決，直接 `git add src/login.py` + `git rebase --continue`，檔案內仍殘留 `<<<<<<<`、`=======`、`>>>>>>>` 以及錯誤的 `LOGIN_TIMEOUT = 45`、`LOGIN_RETRY = 3`，因 `file_contains` 只做子字串比對，竟判 **7/7 全過**。
- **漏洞 B `[AG 發現]`（零遠端更新、零 Fetch、零 Rebase 直接通過）**：完全不按「模擬遠端 main 更新」、不 `fetch`、不 `rebase`，直接修改 `src/login.py` 寫入 `LOGIN_RETRY = 5` 並 commit，一樣判 **7/7 全過**。
- **解法**：
  1. 新增 `no_conflict_markers` 檢查，並將 `src/login.py` 改為整行／正規表示式或完整內容比對（忽略 CRLF/LF），同時排除 `LOGIN_TIMEOUT = 45` 與 `LOGIN_RETRY = 3`。
  2. 檢查本機 `origin/main` 必須等於後端記錄的模擬遠端新 SHA（確認確實按過更新且完成 `git fetch`）。

### P0-3：`[Claude 發現]` 判題信任受測者可自行竄改的 Git ref
- **現象**：
  - Task 01、02、06 使用 `assessment-start..HEAD`，受測者執行 `git tag -f assessment-start HEAD~1` 即可藏匿多餘 commit。
  - Task 03 使用 `main..HEAD` 與 `main` 檔案內容，實測多建一筆無關 commit 再 `git branch -f main <該 commit>` 仍判 **6/6 全過**，但 `main` 已被篡改。
- **解法**：建立 session 時把各題起始 commit SHA、原始 `main` SHA 與模擬遠端目標 SHA 寫入後端 `runtime/results/<session>.json`，判題一律以伺服器端記錄的 SHA 為基準，不信任 repo 內可被改寫的 tag/branch 名稱。

### P0-4：`[Claude 發現]` 重設歸零檢查次數，且重複檢查會覆寫完成時間
- **現象**：
  - `reset_task` 會把 `check_attempts` 歸零，受測者可透過重設隱藏多次失敗紀錄。
  - 已完成題目再點一次「重新檢查」會覆寫 `completed_at`，實測會出現單題完成時間晚於整份測驗完成時間的矛盾。
  - `events` 雖已完整記錄所有檢查與重設，但結果頁與 PNG 均未呈現。
- **解法**：`check_attempts` 改為累計值、新增 `reset_count`、`completed_at` 僅於首次通過時寫入（不覆寫），並在結果頁呈現總作答時間、各題耗時與重設次數。

### P0-5：`[AG 發現]` 多目錄版本並存時，`Start Git Assessment.vbs` 會靜默開啟錯誤實例
- **現象**：[Start Git Assessment.vbs](file:///C:/Users/2606854/.gemini/antigravity/worktrees/git-assessment/newcomer_ux_evaluation/Start%20Git%20Assessment.vbs#L27-L41) 只比對回應 HTML 是否含有 `name="git-assessment-token"`，未驗證是否為同一目錄實例。若電腦上已有舊版目錄占住 port 8765，雙擊新版腳本會靜默開啟舊版網頁。
- **解法**：`/api/health` 回傳實例目錄雜湊（`instance_id`），VBS 偵測到 port 8765 屬於不同目錄實例時，應彈窗提示使用者先關閉舊實例或改用其他連接埠。

## 四、題目問答與新進人員理解度改善

### 1. 逐題觀察與改善重點
- **Task 01（選擇性提交）**：`[共同驗證]` 題意清晰，但新手最常誤用 `git add .` 卻不知道如何撤回（`git reset` / `git restore --staged`）；首次出現 `working tree`、`staging area` 建議括號附中文說明。
- **Task 02（Amend）**：`[共同驗證]` 要求提到 `assessment-start 到 HEAD` 卻未解釋 `assessment-start` 是系統預設 tag；未提醒 `git commit --amend` 預設會開編輯器（Windows 未設 `core.editor` 會卡在 Vim，應補充 `--no-edit` 或 `:wq` 提示）。
- **Task 03（建立功能分支）**：`[共同驗證]` 6 題中最清晰友善，重點在於改用伺服器端原始 `main` SHA 防篡改。
- **Task 04（Fetch + Rebase Conflict）**：`[共同驗證]` 步驟最長、概念門檻最高。
  - `[AG 發現]` 要求第 6 點將原本就存在的 `LOGIN_RETRY`（3→5）寫成「遠端**新增**」，建議改為「遠端**更新後**的 `LOGIN_RETRY = 5`」。
  - `[共同驗證]` 未按按鈕就 `fetch`/`rebase` 時 Git 只會說 `up to date`；且 `git rebase --continue` 同樣會彈出編輯器造成新人卡關，需在說明或「常見卡關」補上教學。
- **Task 05（Stash + 遠端分支）**：`[共同驗證]` 步驟完整但受 P0-1 誤報嚴重干擾；`[AG 發現]` 文案混用 `hotfix/check-status` 與 `Hotfix 分支`，建議統一。
- **Task 06（Cherry-pick）**：
  - `[Claude 發現]` 手動複製檔案再用相同訊息 commit 也能過關，未驗證真的使用 `cherry-pick`。
  - `[AG 發現]` 目前 `fix/validation` 只有 1 筆 commit，與 `main` 距離僅一步，建議擴充為 **2 筆 commit**（第 1 筆為不相關修改、第 2 筆才是空字串驗證修正），才能讓新人真正體會為何不能 `merge` 整個分支。

### 2. 問答與評量機制升級方向
1. **`[共同驗證]` 回饋訊息具象化（實際值 vs 預期）**：將「尚未找到符合要求的 commit message」「Commit 數量不符合任務限制」升級為顯示目前實際觀察到的值（例如 `最新 commit 訊息為「fix config」，需完全等於「Fix configuration loading」`）。
2. **`[Claude 發現]` 區分「練習模式」與「考試模式」**：目前步驟寫得較像「照指令清單輸入」；建議練習模式保留逐步指引與修正建議，考試模式則僅給情境目標與限制（提供可展開的計次提示），以測出真正的 Git 判斷能力。
3. **`[Claude 發現]` 過程驗證補強**：於 Task 02（`reflog` 含 `commit (amend)`）、Task 04（`rebase (finish)` + `origin/main` 指向新遠端 SHA）、Task 06（`cherry-pick` reflog 或 patch-id / author date 比對）驗證操作過程而不只看最終檔案文字。

## 六、系統架構與 API 改善清單

兩份報告均已驗證本機 `X-Git-Assessment-Token`、跨來源 `Origin` 阻擋、雙重確認標頭、`X-Git-Assessment-Request-ID` 冪等性、原子重設與 `quarantine` 備份等核心防線皆正常運作。架構面建議補強以下 8 點：

1. **`[共同驗證]` 修正 HTTP 狀態碼與 JSON 錯誤中文化**：`KeyError`（查無 session / task）改回 `404 Not Found` 而非 `400`；JSON 回應的 404 / 405 也套用中文錯誤訊息（與 HTML 錯誤頁一致）。
2. **`[AG 發現]` 後端補齊 `candidate_name` 長度驗證 & REST 回應一致**：後端同步驗證 `<= 80` 字元（目前實測 120 字元會直接寫入）；`POST /api/sessions` 在 `Accept: application/json` 時回傳 `201 JSON` 而非強制 `302`。
3. **`[Claude 發現]` GET 請求加上 `Host` 標頭白名單**：[security.py](file:///C:/Users/2606854/.gemini/antigravity/worktrees/git-assessment/newcomer_ux_evaluation/app/security.py#L16) 目前僅保護寫入請求，對 GET 加上 `LOCAL_HOSTS` 檢查可消除 DNS rebinding 讀取成績風險。
4. **`[Claude 發現]` 判題引擎擴充與基準外置**：新增 `no_conflict_markers`、`file_equals`、`file_matches`、`reflog_contains_action`、`patch_equivalent`，並從伺服器端結果檔讀取基準 SHA。
